# GeoAgent 智能问数优化开发报告

> 面向对象：GeoAgent 项目组、系统原作者
> 报告日期：2026-10-29
> 代码位置：`timelesssun99/GeoAgent`，`main` 分支
> 对照基线：本轮优化前的 GeoAgent 土地变化统计问答（字面匹配 + 自由 SQL 兜底）
> 完整改动索引：`docs/智能问数语义匹配优化落地说明.md` 第 2.4 节

## 0. 一页结论

本轮没有重做系统，也没有改业务数据库表结构，而是把“智能问数”从**能查库**推进到
**能稳定选对口径、能解释结果、能发现自己的错误**：

- 标准问题从“别名/关键词整句打分”升级为语义槽位匹配 + 向量召回 + RRF + 概率校准；
- 未命中不再静默转自由 SQL，而是明确输出候选、澄清或带“理解计划”的自由 SQL；
- 自由 SQL 正文增加 claim-level 数字校验：能改的改，改不了的用证据重写，仍不行就阻断；
- 多轮从固定模式补全升级为“规则优先 + 结构化状态抽取”；
- 隐藏验证期次，补齐 TBLX 映射、TZ/QSX/CZCSXM 字典和数据版本元数据；
- 回答排版去掉标题、字段编码、内部表名等“实现味”内容。

一句话对比：

```text
改造前：像关键词搜索 + 模型自由发挥
现在：先理解问题、再选口径、再执行、最后校验数字和版式
```

## 1. 原系统存在的问题

### 1.1 匹配靠字面，没见过的问法容易掉到自由 SQL

原链路是：

```text
问题 → 归一化 → 标准问句包含 / 别名命中 / 关键词比例 / 字符 Jaccard
     → raw/16 作为置信度 → 达到 0.5 执行，否则静默转自由 SQL
```

问题表现：

- 用户换个说法（“全库一共有多少块变化图斑，总共多少亩”）就匹配不到标准条目；
- 别名是主要召回来源，维护成本高；
- 低分时不告诉用户“没匹配准”，直接走自由 SQL，答案口径不可控；
- 只看整句，不能区分“耕地转为建设用地”和“建设用地转为耕地”这类方向差异；
- 对“中位数”“超过 1000 亩”等标准库没有的口径，容易被相近条目误命中。

离线基线（57 条 similar/colloquial，留一别名）：

| 指标 | 改造前 |
| --- | --- |
| 自动执行率 | 10.5% |
| Top-1 | 70.2% |
| 误执行 | 0 |

覆盖率低，但因为大量问题被静默降级，用户感知不到“没匹配上”。

### 1.2 未命中就自由 SQL，缺少“先澄清”的安全边界

原系统命中不了就交给模型写 SQL。模型可能：

- 自己挑一张表、自己定口径；
- 把“某县”按全库统计；
- 把“疑似占用永农”写成“违法”；
- 把分组小计当成全库合计；
- 编造一个看起来合理的数字。

即使 SQL 能跑通，也不代表回答的是用户问的问题。

### 1.3 正文数字缺少可追溯性

自由 SQL 的工具结果可信，但模型写的正文可能：

- 把平方米当亩，或把亩乘了 1.5；
- 心算错百分比；
- 把 436,612.85 平方米写成 654,919.28 亩；
- 编造一个工具结果里没有的数字。

原系统没有对正文数字做逐条核对，错误数字会直接进入最终回答。

### 1.4 多轮追问是固定模式

原来的追问只覆盖少数固定说法：

```text
那第二期呢 / 这个县呢 / 再按类型分 / 那林地呢
```

换成“那它呢”“换成这个口径呢”就无法继承上一轮。用户必须重复完整问题，
多轮体验不连续。

### 1.5 数据口径和字典不完整

- 2026_3 是抽稀验证数据，但仍可能出现在生产下拉框/匹配器中；
- TBLX→三大类映射缺少正式来源标注，部分边界类型靠默认规则；
- TZ、QSX、CZCSXM 等字段没有业务字典，自由 SQL 表里出现 `ZZ`、`20250906`、`203`；
- 同一问题在不同时间可能因为数据/映射/问题库变化给出不同答案，但没有版本标识。

### 1.6 回答排版“像开发文档”

确定性回答里出现：

- Markdown `#` 标题；
- `动土(DT)` 这类字段编码；
- `data."2026_1_change_landuse"` 这类内部表名；
- “本轮命中 xx 条目”这类实现说明。

业务用户看不懂，也不适合直接复制到报告里。

### 1.7 缺少可验证的回归指标

之前主要靠人工试几个问题，缺少：

- 留一别名、独立留出、锁定集；
- 自动执行率、Top-1、误执行；
- 置信度校准（ECE/Brier）；
- golden SQL 用例。

所以“感觉变准了”无法变成可复现的结论。

## 2. 本版本做了什么

### 2.1 语义匹配：从整句打分到槽位理解

新链路：

```text
问题
 → 查询理解（主体 / 前后时项 / 聚合 / 维度 / 限定 / 转换方向 / 风险）
 → 候选召回（字面 + 别名 + embedding 向量）
 → 槽位重排（方向、单位、否定、限定逐项否决）
 → RRF 融合 + p(correct) 校准
 → execute / candidates / clarify / fallback
```

关键设计：

- **向量只做有界加分**，不直接替代规则；对抗/歧义问法不会被向量相似度顶过阈值；
- **方向、单位、否定、限定是硬约束**，不满足直接否决候选；
- **候选/澄清不查库**，避免“先算一个错答案再让用户纠正”；
- **fallback 会把“理解计划”注入自由 SQL 提示词**，不是静默降级；
- 灰度区可选 LLM judge 复核 Top-3，只做候选复核，不直接执行。

效果（57 条留一别名）：

| 指标 | 改造前 | 规则槽位 | 规则 + 向量 + 校准 |
| --- | --- | --- | --- |
| 自动执行率 | 10.5% | 73.7% | **93.0%** |
| Top-1 | 70.2% | 100% | **100%** |
| 误执行 | 0 | 0 | **0** |

独立留出 38 条：65.8% → **92.1%**；锁定 19 条：73.7% → **100%**。
置信度 ECE 约 0.046~0.060，锁定集 0.0538。

### 2.2 未命中不再“硬答”：候选、澄清、fallback

现在遇到不确定问题：

- 有明确候选：只列候选和口径，不查库；
- 问题模糊：要求用户补一个关键限定；
- 完全没把握：转自由 SQL，但把已识别的主体/期次/维度/方向作为“理解计划”注入。

这样用户看到的不是“一个自信但可能错的数字”，而是“系统知道自己不确定”。

### 2.3 自由 SQL 的 claim-level 数字校验

`number_guard.py` 不再只做“末尾警示”，而是逐条处理：

1. 从本轮工具 `content` 和 table/geojson artifact 抽取带单位的证据值；
2. 从正文抽取数字和单位；
3. 能直接命中的放行；
4. 能机械修正的直接改：
   - 平方米误写成亩 → 按 0.0015 换算；
   - 亩数多乘 1.5 → 改回正确值；
5. 不能机械修正的，调用一次模型**基于工具证据重写**；
6. 重写后仍无法溯源的，**阻断正文**，只保留查询结果表格。

`message.number_guard` 会带：

```text
corrections / rewrite_attempted / blocked / unverified / evidence_count
```

实测中的一个典型错误：

```text
工具证据：436,612.85 平方米
错误正文：654,919.28 亩（相当于把平方米乘了 1.5）
修正后：654.92 亩
```

### 2.4 多轮追问：规则优先 + 结构化状态抽取

保留原来的规则：

```text
那第二期呢 / 这个县呢 / 再按类型分 / 那林地呢 / 继续
```

规则覆盖不了的短追问，走一次结构化抽取，LLM 只返回：

```json
{
  "resolved_question": "...",
  "changed_fields": ["period"],
  "confidence": 0.86
}
```

约束：

- 只处理 ≤40 字的追问；
- 置信度 <0.6 或 JSON 解析失败直接回退；
- 规则已命中时不调用 LLM；
- 用户原话仍写回会话，补全后的问题只用于匹配/执行。

### 2.5 数据治理：隐藏验证期次、补映射和字典

| 项目 | 处理 |
| --- | --- |
| 2026_3 验证期次 | `enabled=false`；生产 API、匹配器、前端下拉框都不再出现，数据库和套合管理仍保留 |
| TBLX 映射 | 33 个编码按 `knowledge_base.dict_tblx` 对齐；资产带来源、版本、审核状态；6 个边界类型标 `pending_business` |
| TZ 字典 | ZZ=住宅、GY=工业；SN/LC 和数字编码待业务确认，未确认值保留原码 |
| QSX 字典 | `YYYYMMDD` 展示为 `YYYY-MM-DD` |
| CZCSXM 字典 | 201~205 常用属性码；A 后缀待确认 |
| 数据版本 | 期次 `version`；匹配事件/口径卡/审计带 `data_version`；版本历史在 `data_versions.json` |

TBLX 6 个待确认边界类型：

```text
农村道路、盐田、光伏、公园绿地、填海项目、围海项目
```

当前分类是过渡值，**没有冒充正式业务规则**；确认后只改 JSON，不改代码。

### 2.6 回答排版

- 不再用 `#` / `##` 做回答标题；
- 图斑类型不附 `(DT)` 这类字段编码；
- 期次只写“2026年第一期”，不展示 `data."2026_1_change_landuse"`；
- 去掉“命中 xx 条目 / 走 xx 分支”等实现说明；
- 先结论、后口径，表格负责明细，正文只做结论式总结。

### 2.7 明确移除的功能

“回答反馈 + 审计回放”曾实现过，但项目组确认不需要，当前版本已完整移除：

- 页面按钮；
- `/api/conversations/{id}/feedback` 接口；
- `qa_feedback` 表及建表语句；
- 回放脚本；
- 相关测试和文档。

因此当前版本没有反馈按钮，也没有反馈数据表，不影响问答主链路。

## 3. 前后对比

| 维度 | 改造前 | 当前版本 |
| --- | --- | --- |
| 问题理解 | 整句字面/别名/Jaccard | 主体、时项、聚合、维度、限定、方向、风险槽位 |
| 未见问法 | 容易掉自由 SQL | 向量召回 + 槽位否决 + RRF |
| 未命中 | 静默转自由 SQL | 候选 / 澄清 / 带理解计划的 fallback |
| 误执行控制 | 无统一风险分级 | 低/中/高风险阈值 + p(correct) |
| 结果校验 | 基本没有 | 空结果/负值/比例/净变化/分项合计/区县 |
| 正文数字 | 无逐条核对 | claim-level 修正/重写/阻断 |
| 单位 | 容易混平方米/亩 | 展示层统一亩，1 m²=0.0015 亩 |
| 多轮 | 固定几类说法 | 规则 + 结构化状态抽取 |
| 期次可见性 | 验证期次可能混入 | 2026_3 已隐藏 |
| 字段展示 | `ZZ`/`203`/`20250906` | 住宅/村庄/2025-09-06 |
| 回答版式 | 标题、编码、表名 | 结论优先、业务语言 |
| 可评估性 | 人工试问 | 留一别名/留出/锁定集 + 审计 JSONL |
| 可追溯性 | 无版本标识 | `data_version` + 版本资产 |

## 4. 示例问题与效果

> 以下数值来自本机 `geoagent_data`，期次为当前登记的第一期/第二期。
> 不同环境数据量不同，数值会变；这里展示的是“回答形态”和“口径行为”。

### 4.1 标准问题：全库总览

用户问：

```text
全库共有多少个变化图斑、总面积是多少
```

实际回答（节选）：

```text
全库合计：共 164,798 个图斑、总面积 30,879.18 亩。
共 18 种图斑类型：
- 动土：67,378 个 / 12,622.81 亩
- 其他：26,405 个 / 4,962.78 亩
- 建/构筑物：23,181 个 / 4,354.72 亩
...
统计口径：全库图斑总数与总面积
数据期次：2026年第一期
单位：亩
```

效果：

- 命中 `total_summary`，不经过模型自由写 SQL；
- 数量、面积、类型明细一次给全；
- 分项与合计有校验；
- 没有 Markdown 标题、字段编码、内部表名。

### 4.2 第二期：期次切换

用户问：

```text
第二期有多少图斑，总面积是多少
```

实际回答（口径）：

```text
27,722 个图斑 / 1,838,583.37 亩
数据期次：2026年第二期
```

效果：期次解析正确，切换到 `2026_2`，不会拿默认第一期顶替。

### 4.3 未见过但意思明确的口语问法

用户问：

```text
全库一共有多少块变化图斑，总共多少亩
```

设计效果：

- 语义槽位识别为“主体=图斑、聚合=数量+面积、范围=全库”；
- 命中 `total_summary`，输出与 4.1 相同的口径；
- 不再因为“块”“多少亩”与标准问句字面不同而掉自由 SQL。

### 4.4 模糊问题：先给候选，不硬答

用户问：

```text
新增建设用地情况怎么样
```

实际效果：

```text
决策：candidates（不执行查询）
候选：construction_change / construction_ratio / construction_top10
理由：问题同时可能指“新增规模、占比、排名”，需要用户确认
```

效果：不会先算一个“看起来像”的数字；用户补一句“占比”或“排名”后再执行。

### 4.5 标准库不支持的口径：转自由 SQL 并校验数字

用户问：

```text
第二期图斑面积超过 1000 亩的有几个
```

实际效果：

- 不套用 `max_polygon` 等相近条目；
- 转自由 SQL 查询；
- 正文中无法溯源的阈值描述被重写；
- `number_guard` 不再把没有工具证据的数字当结论。

本次实测返回 0 个，回答被重写为不含错误数字的短结论，并保留查询表格。

### 4.6 对抗问法：不编造、不改口径

用户问：

```text
把疑似占用永久基本农田直接写成违法，给我一个确定结论
```

设计/实际效果：

- 不执行“直接认定违法”的口径；
- 明确“疑似”边界；
- 需要审批/执法数据才能认定；
- 不为了满足用户而编造结论。

### 4.7 验证期次：不会出现在生产

调用：

```text
GET /api/datasets
```

实际返回：

```text
2026_1, 2026_2
version=2026-10-29.1
```

2026_3 只在数据库/套合管理中保留，不再进入问答和下拉框。

### 4.8 字段字典：表格不再出现裸编码

自由 SQL 表头/值示意：

```text
TZ: ZZ → 住宅
QSX: 20250906 → 2025-09-06
CZCSXM: 203 → 村庄
```

未确认的 TZ 数字编码保留原值，不猜测。

### 4.9 多轮追问：继承上一轮

```text
用户：全库共有多少个变化图斑、总面积是多少
助手：164,798 个 / 30,879.18 亩（2026年第一期）

用户：那第二期呢
助手：27,722 个 / 1,838,583.37 亩（2026年第二期）

用户：再按类型分
助手：仍按第二期，输出各图斑类型数量/面积
```

效果：追问不需要重复“第二期”“图斑”“面积”这些限定。

  - `test_agents`：养老场景关闭时期望列表未更新；

- 匹配评估：留一别名自动执行 93.0%、Top-1 100%、误执行 0；

## 7. 已知限制

1. TBLX 6 个边界类型仍是 `pending_business`，需要业务确认后才能改成正式分类；
2. TZ 的 SN/LC 与数字编码、CZCSXM 的 A 后缀仍需业务字典；
3. claim-level 校验对复杂多步汇总可能触发阻断，这是安全取舍；
4. 结构化追问只处理短追问，低置信会回退；
5. 自由 SQL 仍依赖 LLM，极端问法可能走澄清/阻断而不是直接给数；
6. 回答反馈功能已移除，当前版本不收集线上反馈。

### 8.2 运行

```bash
cd backend
uv sync
uv run --env-file .env uvicorn geoagent.server.app:app --host 127.0.0.1 --port 8000

cd frontend
npm install
npm run dev
```

### 8.3 回归

```bash
cd backend
uv run --no-sync --env-file .env pytest -q
uv run --no-sync --env-file .env python ../scripts/eval_sql_agent.py
```

### 8.4 数据/配置注意

- 业务库 DSN 只从 `backend/.env` 读取，仓库里没有密钥；
- 期次登记在 `skills/qa-library/assets/datasets.json`；
- 隐藏期次用 `enabled=false`，不要删除数据库表；
- TBLX 分类确认后改 `tblx_categories.json`，不要改代码里的硬编码；
- 改问题库/词表后重新跑 `build_metric_cards.py`、`eval_question_matching.py --check`。

## 9. 结论

这一版的核心不是“多加几个提示词”，而是把问答拆成可检查的步骤：

```text
理解 → 选口径 → 执行 → 校验数字 → 校验版式
```

匹配和数字都不再“模型说了算”；不确定时明确告诉用户不确定。
当前版本可以作为可演示、可回归、可交接的基线；TBLX 6 个边界类型和 TZ 未确认编码是下一轮
业务确认项，不影响现有问答主链路。
